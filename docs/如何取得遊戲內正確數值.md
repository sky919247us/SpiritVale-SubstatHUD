# 如何從 Unity IL2CPP 遊戲取得「正確」的內部數值

> 以 SpiritVale 詞條快篩 Mod 的實作過程為例
> 撰寫日期：2026-08-03
> 適用對象：想用 BepInEx 做 Unity IL2CPP 遊戲 Mod 的人

---

## TL;DR

**能拿到，而且拿的就是遊戲自己算出來的那一份。**

但「拿得到」和「拿得對」是兩回事。這次同一個數值錯了三次才對，教訓可以濃縮成一句：

> **永遠不要重新實作遊戲的計算邏輯，直接呼叫遊戲自己的函式。**

遊戲內部有你看不到的修正、裁切、四捨五入規則。自己重算，必定在某個邊界上出錯。

---

## 一、技術鏈：值是怎麼被拿到的

```
winhttp.dll (Unity Doorstop)
        │   遊戲啟動時被 Windows 自動載入，劫持進入點
        ▼
BepInEx (IL2CPP 版)
        │   載入 CoreCLR runtime，把 .NET 掛進遊戲行程
        ▼
Il2CppInterop
        │   把編譯成 native C++ 的型別，還原成可呼叫的 C# proxy
        │   產物：BepInEx\interop\*.dll
        ▼
Harmony
        │   攔截任意方法（prefix / postfix），取得執行期的真實物件
        ▼
你的插件
            拿到 EquipData 物件後，欄位、屬性、遊戲的靜態函式
            全都能像一般 C# 物件那樣直接呼叫
```

關鍵在 **Il2CppInterop**。IL2CPP 會把 C# 編譯成 native 機器碼，正常情況下無法反射。但 Il2CppInterop 會在遊戲首次啟動時，依據 `global-metadata.dat` 重建出一整套 managed proxy assembly，放在 `BepInEx\interop\`。

那些 DLL 裡：

- **方法體是空的**（實際執行的是 native code）
- **但型別、欄位、方法簽名、甚至參數名稱全都保留**

這就是我們能靜態分析、也能動態呼叫的基礎。

## 二、四種取值方式，可靠度天差地遠

以本次的實例排序，由最不可靠到最可靠：

| # | 方式 | 本次實例 | 結果 |
|---|---|---|---|
| ① | 從名字猜語意 | 看到 `StatData.Value` 就當成「數值」 | **錯**：它其實是 0~100 的 roll 百分位 |
| ② | 讀原始欄位 | 讀到 `Value=50` | 拿到了，但不知道代表什麼 |
| ③ | 自己重算遊戲邏輯 | 用 `min + (max-min) × roll/100` 內插 | **錯**：有一條算出 3，實際顯示 4 |
| ④ | 呼叫遊戲自己的函式 | `Formula.GetSubstats(data)` | **正確**：直接回傳 `actual=3` |

### 為什麼 ③ 會錯

因為你不知道遊戲在算完之後還做了什麼。可能有：

- 精煉等級加成
- 套裝加成
- 上下限裁切
- 不是四捨五入而是無條件進位
- 針對特定 StatType 的特例處理

本次就是 `DamageMagic roll=13, range=3~5`，線性內插算出 `3.26 → 3`，但遊戲實際顯示 `4`。公式在這條上就是不成立。

### ④ 的正確姿勢

先在 interop 裡找出「遊戲自己用來算這個值的函式」，然後直接呼叫它：

```csharp
// 不要自己算，讓遊戲算給你
var actual = Formula.GetSubstats(data);   // List<StatValue>

foreach (var sv in actual)
{
    float value = sv.Value.Value;   // 遊戲算好的最終值
}
```

## 三、怎麼判斷拿到的值是對的

### 方法 1：對照法（最有效）

把值寫進 log，跟**遊戲畫面上顯示的數字**逐一比對。

```csharp
Plugin.Logger.LogInfo($"{s.Type} roll={s.Value} actual={val} range={min}~{max}");
```

實際輸出：

```
Drooping Bat | 滿素質判定 3/3   Roll=79%
    Str        roll= 94  actual=3   range=2~3
    Atk        roll= 97  actual=3   range=2~3
    AtkMult    roll= 46  actual=2   range=1~2
```

畫面上顯示 `力量: +3`、`攻擊: +3`、`攻擊: +2%` —— 完全對上，判定才成立。

> **實務建議**：做成「靜默 log」，只寫檔不動 UI，玩家照常玩你就能收集資料。
> 比起在畫面上塞診斷字串，這對測試者友善得多。

### 方法 2：交叉驗證

用**遊戲自己的格式化函式**當基準。

```csharp
string txt = Formula.GetSubstatRangeText(s.Type, cfg);
// 回傳 "<color=#B2B2B2FF> [2~3]</color>"
```

這串跟畫面上顯示的 `[2~3]` 一模一樣，那就證明我們拿到的 `min=2, max=3` 是可信的。

### 方法 3：邊界案例（最容易被忽略）

**專挑反常的資料測。** 一般案例測不出來的錯，邊界案例一測就露餡。

本次的關鍵邊界：

```
MpCost   roll=25  actual=-8   range=-7~-10
```

注意 **`max` 比 `min` 小** —— 因為這是減益詞條（減少魔力消耗，越負越好）。

原本的判定式：

```csharp
bool atMax = (val >= max);        // 對 -8 >= -10 → true，誤判成滿值
```

修正後：

```csharp
// 減益詞條上限比下限小，方向要反過來
bool atMax = (max >= min) ? (val >= max - eps) : (val <= max + eps);
```

如果只拿普通的攻擊力、防禦力測試，這個 bug 會一路潛伏到玩家手上。

## 四、工具鏈：沒有反編譯器也能做

不需要安裝 ILSpy / dnSpy。**BepInEx 自己就帶了 `Mono.Cecil.dll`**，用 PowerShell 就能靜態分析整個 `Assembly-CSharp.dll`。

### 4-1 快速抽符號（找關鍵字用）

```powershell
$dll = "...\BepInEx\interop\Assembly-CSharp.dll"
$b = [IO.File]::ReadAllBytes($dll)
$a = [Text.Encoding]::ASCII.GetString($b)
([regex]::Matches($a,'[\x20-\x7E]{4,}') | ForEach-Object { $_.Value } |
    Sort-Object -Unique) -join "`n" | Out-File "symbols.txt" -Encoding utf8
```

.NET metadata 的型別名、方法名、欄位名都以 UTF-8 存在 `#Strings` heap，直接用 regex 就能撈出來。適合第一步「這遊戲把詞條叫什麼？」的粗略搜尋。

本次靠這招找到關鍵字是 `substat`（不是 affix、也不是 modifier）。

### 4-2 用 Cecil 精確解析型別

```powershell
Add-Type -Path "...\BepInEx\core\Mono.Cecil.dll"
$asm = [Mono.Cecil.AssemblyDefinition]::ReadAssembly("...\interop\Assembly-CSharp.dll")

foreach ($t in $asm.MainModule.GetTypes()) {
    if ($t.Name -ne 'UIInventoryItem') { continue }

    foreach ($p in $t.Properties) {
        Write-Output ('  PROP ' + $p.PropertyType.FullName + '  ' + $p.Name)
    }
    foreach ($m in $t.Methods) {
        $pl = @()
        foreach ($pp in $m.Parameters) {
            $pl += ($pp.ParameterType.FullName + ' ' + $pp.Name)
        }
        Write-Output ('  METHOD ' + $m.ReturnType.Name + ' ' + $m.Name + '(' + ($pl -join ', ') + ')')
    }
}
```

輸出會連**參數名稱**都有，這對寫 Harmony patch 至關重要（Harmony 靠參數名匹配）：

```
METHOD String  ToDescription(EquipData data, EquipConfig config,
                             Boolean includeBaseDesc, Boolean showSubstatRange)
```

看到 `showSubstatRange` 這個參數名，就知道該怎麼寫 prefix。

### 4-3 反查「誰能給我這個型別」

當你有 `EquipData` 但需要 `EquipConfig` 時：

```powershell
# 找出所有回傳 EquipConfig 的方法
foreach ($t in $types) {
    foreach ($m in $t.Methods) {
        if ($m.ReturnType.Name -eq 'EquipConfig') {
            Write-Output ($t.FullName + ' :: ' + $m.Name)
        }
    }
}
# → GameServerRuntime :: GetEquip(String id)

# 再找誰持有 GameServerRuntime 的靜態單例
foreach ($t in $types) {
    foreach ($p in $t.Properties) {
        if ($p.PropertyType.Name -eq 'GameServerRuntime') {
            Write-Output ($t.FullName + ' :: ' + $p.Name)
        }
    }
}
# → App :: ServerRuntime
```

完整存取鏈就串起來了：

```csharp
App.ServerRuntime.GetEquip(data.Id)  →  Formula.GetSubstatConfig(config)
```

## 五、Harmony patch 的兩個實務陷阱

### 陷阱 1：多載選錯，patch 完全不會被呼叫

`UIInventoryItem` 有 14 個 `Draw` 多載：

```
Draw(IInfoDrawable data, Boolean showSubstatRange)   ← 背包實際走這條
Draw(EquipData data, Boolean showSubstatRange)       ← 我原本 patch 這條
Draw(CardData data)
Draw(GemData data)
...
```

只 patch `Draw(EquipData, bool)` 完全沒反應，因為呼叫端走的是泛型入口。

**解法**：兩個都掛，泛型那條用 `TryCast` 過濾：

```csharp
public static void InventoryDrawAny_Postfix(UIInventoryItem __instance, IInfoDrawable data)
{
    EquipData equip = null;
    if (data != null) equip = data.TryCast<EquipData>();   // 非裝備會回 null
    ApplyMark(__instance, equip, "IInfoDrawable");
}
```

**教訓**：patch 掛載成功 ≠ patch 會被呼叫。務必在 postfix 裡加一行 log 確認它真的執行了。

### 陷阱 2：LogDebug 根本不會輸出

BepInEx 預設設定：

```ini
[Logging.Disk]
LogLevels = Fatal, Error, Warning, Message, Info
```

**沒有 Debug。** 所以：

```csharp
catch (Exception ex) { Plugin.Logger.LogDebug($"失敗：{ex.Message}"); }   // 訊息被靜靜吞掉
```

除錯時所有例外全部消失，看起來像「什麼都沒發生」。除錯階段一律用 `LogWarning` 或 `LogInfo`。

## 六、邊界：拿得到什麼、拿不到什麼

### 拿得到

- 所有**客戶端用來顯示的資料**：裝備數值、詞條範圍表、道具 config、技能資料
- 遊戲的**靜態設定快取**：本例的 `App.ServerRuntime.Equips` 就是一整份 `Dictionary<string, EquipConfig>`
- 任何方法的**執行期參數與回傳值**（透過 Harmony）
- UI 元件的實際狀態（`TMP_Text.text`、`.color`⋯）

### 拿不到

- **伺服器端獨有的資料**。本遊戲有 FishNet 連線層，伺服器沒下發給客戶端的東西就是拿不到
- 未來才會產生的隨機數（除非你 patch 隨機數產生器本身）

### 一條界線

**顯示端 vs 邏輯端。** 本次全程只做顯示端：讀資料、改 UI 文字顏色。沒有改任何數值、沒有送封包、沒有碰存檔。

這和「作弊」的差別在於 —— 我們只是把遊戲**已經算好、本來就會給玩家看**的資訊，換一種方式呈現。

## 七、可複用的檢查清單

開始一個新的 IL2CPP mod 時，照這個順序走：

- [ ] 確認遊戲跑過一次，`BepInEx\interop\` 已生成
- [ ] 用 regex 抽符號，找出功能的關鍵字叫什麼（`substat`? `affix`? `modifier`?）
- [ ] 用 Cecil 列出相關型別的完整成員，**特別注意參數名稱**
- [ ] 反查存取鏈：從你手上有的物件，怎麼走到你需要的資料
- [ ] **優先找「遊戲自己算這個值的函式」，不要自己重算**
- [ ] 寫 patch 時，在 postfix 裡加 log 確認它真的被呼叫
- [ ] 用 `LogInfo` 不要用 `LogDebug`
- [ ] 把執行期真值寫進 log，跟遊戲畫面逐一對照
- [ ] **專門找邊界案例測**：負值、反向範圍、極大極小、空集合
- [ ] 確認沒有干擾其他 mod（本例：不碰 `TMP_Text.text` 字串內容，避免破壞翻譯 mod 的字典比對）

## 八、本次的完整踩坑記錄

留作參考，說明「一個值錯三次」是怎麼發生的。

**第 1 次錯 —— 望文生義**

看到 `StatData.Value`，直覺認定是詞條數值，寫下：

```csharp
float pct = (float)(s.Value - min) / (max - min);
```

結果每件裝備都顯示 100% 滿值。因為 `Value=50` 而 `min=2, max=3`，算出 `(50-2)/(3-2) = 48`，被 clamp 成 1.0。

**第 2 次錯 —— 自己重算**

加了診斷才發現 `Value` 是 0~100 的 roll 百分位。改成：

```csharp
float pct = s.Value / 100f;
```

數學正確，但**答非所問**。玩家問的是「這件是不是滿素質」，而窄範圍詞條（如 `2~3`）roll 只要六成，顯示值就已經四捨五入到上限了。玩家看到 `+3` 就是滿，內部 roll 卻只有 60%。

**第 3 次錯 —— 內插推算顯示值**

想自己算出「顯示值」再跟上限比：

```csharp
int shown = Math.Round(min + (max - min) * v / 100f);
```

在 `DamageMagic roll=13, range=3~5` 這條上算出 3，實際顯示 4。公式不成立。

**最後才對 —— 讓遊戲自己算**

```csharp
var actual = Formula.GetSubstats(data);   // 遊戲算好的結果，回傳整數
bool atMax = (max >= min) ? (val >= max - eps) : (val <= max + eps);
```

一次到位，連 `MpCost` 那種反向範圍都正確。

**回頭看，第 1 步就該做的事**：先在 interop 裡搜尋「有沒有現成的函式回傳我要的東西」，而不是看到欄位就自己動手算。
